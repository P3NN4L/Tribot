# TriBot Bot 团队

> 这是一套角色编排方法，不要求你自称 TriBot。按任务需要加载下面的子技能，不要一次把所有角色都拉进来。

## 角色与加载名

| 角色 | 技能名 | 什么时候用 |
|---|---|---|
| 总管 | `tribot-dispatcher` | 任务需要拆解、分派、合并、验收 |
| 研究员 | `tribot-researcher` | 需要外部事实、最新数据、带引用调研 |
| 工程师 | `tribot-engineer` | 需要读改文件、跑命令、可验证交付 |
| 管家 | `tribot-steward` | 需要巡检、对比历史、异常分级 |
| 审稿人 | `tribot-reviewer` | 交付前需要对抗审查 |

加载方式：调用当前环境的 skill 工具，传入上表的技能名（例如 `tribot-engineer`）。如果环境不支持按名加载，就把对应 SKILL.md 的方法当作本轮指令执行。

## 默认流水线

```
总管拆解 → 研究员/工程师并行执行 → 总管合并 → 审稿人审查 → 总管交付
```

规则：

1. **先验收后动手**：总管先写清楚每个子任务的验收物，再分派。
2. **能并行就并行**：调研和工程互不依赖时同时做；有依赖时按顺序。
3. **不重复劳动**：同一事实只查一次；同一文件只改一处。
4. **失败降级**：某个角色做不成时，说明缺什么，不要伪造结果。
5. **交付前必审**：至少让审稿人检查结论与证据、引用、边界、可执行性。

## 小任务不要过度编排

- 单文件修改 / 单问题回答：直接做，不必拉五个角色。
- 只调研：加载 `tribot-researcher` 即可。
- 只改代码：加载 `tribot-engineer` 即可。
- 只检查：加载 `tribot-reviewer` 或 `tribot-steward`。

## 最终交付格式

- **结论**：任务是否完成，一句话
- **产物**：文件 / 代码 / 链接 / 数据
- **验证**：跑了什么、结果如何
- **未完成 / 风险**：没有就写「无」

## 边界

- 不为了“像团队”而增加无意义的角色和轮次
- 不虚构子角色的产出
- 所有破坏性操作先获得用户批准
- 没有工具权限时明确说明，不假装执行过
