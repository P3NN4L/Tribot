# 角色方法论（为什么专家 Bot 比通用 Agent 更适合）

## 问题

大多数「多 Agent」产品只是给同一个通用提示词换个名字和头像：

```
You are a helpful assistant. You have tools: ...
```

结果就是：研究员不一定会做研究，工程师不一定会验证。角色是装饰，不是能力。

## TriBot 的做法：四层角色画像

每个内置角色由 `packages/core/src/bots/roles.ts` 定义，包含四层：

| 层 | 作用 | 例子（研究员） |
|---|---|---|
| 身份 | 约束职责边界 | 「你只对可验证的事实负责，没有来源等于没做」 |
| 方法 | 可执行的步骤，不是形容词 | 三角度拆题 → 中英关键词 → 打开原文 → 来源分级 A/B/C → 两源交叉验证 → 冲突裁决 → 停止条件 |
| 质量门槛 | 什么算合格 | 结论至少 1 个 A 级来源或 2 个独立 B 级；单一来源必须标注 |
| 输出契约 | 强制结构，引擎可校验 | 结论 / 要点（带来源）/ 冲突 / 不确定 |

再叠加两个运行时差异：

- **工具隔离**：研究员没有 `write_file`，工程师没有 `web_search`，审稿人只能读。角色不能越界做事。
- **思考档位**：总管/工程师/审稿人 deep，研究员 standard，管家 fast。温度与工具轮次随之变化。

## 五个角色，五套方法

| 角色 | 方法论核心 | 独有机制 |
|---|---|---|
| 总管 | 拆解 → 分派 → 验收 → 合并 | assign 五段模板（目标/输入/交付物/验收/禁区）；冲突按证据等级裁决 |
| 研究员 | 多角度检索 → 读原文 → 来源分级 → 交叉验证 | A/B/C 来源分级；单一来源标注；冲突裁决规则 |
| 工程师 | 复现 → 阅读 → 计划 → 最小改动 → 验证 | 调试协议（二分定位、贴原始报错）；两轮失败即停 |
| 管家 | 清单化 → 取数 → 判级 → 去噪 | 阈值 + 严重度矩阵；Routine 对比上次基线 |
| 审稿人 | 对抗审查：结论/引用/边界/可执行性 | 严重度分级；只列最小修改清单 |

## 为什么这比通用 Agent 更好（可检验，不靠形容词）

1. **结构可测**：输出契约是字符串校验，`missingContract()` 能直接算出缺了哪一节。通用 Agent 的「详细一点」无法度量。
2. **方法可复用**：检索三角度、来源分级是固定步骤，不依赖模型当天的心情。
3. **越界可阻止**：工具隔离在工具层生效，不靠提示词自觉。
4. **缺项可修复**：契约校验失败会提示「补上来源」，用户一句话就能触发补写。
5. **质量有第二双眼睛**：审稿人独立审查，专找无来源数字、夸大结论、缺边界。

## 怎么评估（建议的评测设计）

同一批任务分别用「通用提示词」和「角色画像」跑，按下面维度打分：

| 维度 | 通用 Agent | 角色画像 | 度量方式 |
|---|---|---|---|
| 结构完整 | 常常缺节 | 契约强制 | 小节覆盖率 |
| 来源可点开 | 时有时无 | 强制分级 | 有效链接数 / 结论数 |
| 结论与证据一致 | 容易夸大 | 审稿人拦截 | 人工或 LLM 评审 |
| 可执行 | 缺参数 | 工程师协议 | 步骤可复现率 |

本仓库暂未内置真实模型评测脚本（需要 API Key 与网络）。机制与契约校验已经在代码里，接上 Key 后可以用固定任务集跑上面四个指标。
